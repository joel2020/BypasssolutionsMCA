# Client CRM updates implementation plan

Goal: implement the client's requested Leads status, submission overview, full-screen documents and Elite-style funding-partner details, preserving Bypass layout.

Architecture: extend existing components/hooks and database tables. Lead contact status is separate from underwriting stage, so selecting a disposition never sends a file or changes a funding decision. Reuse private document URLs, existing notes and lender-submission records. No new dependencies.

- [x] Add nullable `leads.lead_status` constrained to New lead, Contacted/Qualified, Low rev/Not interested, Unresponsive, Missing docs, Submitted. Derive existing-row defaults from pipeline status. Add checked inline saves and a status filter in Applications.tsx. Test all six values and persistence/error handling.
- [x] Add a shared deal-notes composer in the overview sidebar and Notes tab. Use an authenticated, permission-checked RPC that derives the author from the active profile; timestamped entries persist without overwriting prior notes. Refresh on window focus and allow manual refresh. Preserve existing lead notes as a separate visible summary. Test author, blank text and cross-client access.
- [x] Load lender submissions for all applications of the current lead, never query all lenders when the lead/application is missing. Show the existing submission list in Overview with dates, status and sent-file indication. Test same-lead isolation.
- [x] Make Documents use the full content width and render its viewer through a body portal at viewport size, with Escape/close, new-tab fallback and readable images/PDFs. Test portal placement and URL-load errors; visually verify full-screen PDF.
- [x] Extend funding partner create/edit fields to match Elite: submission email, additional CC emails, portal/method, minimum funding, minimum months, FICO, positions/negative days/NSFs, decision days, states, products, restricted industries, required documents, criteria and bonus notes. Retain existing contact/revenue/maximum/industry/status/notes fields. Validate email lists, URL protocols and numeric bounds. Use nullable unspecified numeric criteria. Keep current list/detail layout.
- [x] Route Gmail To to submission_email with contact-email fallback; CC contact email plus additional CCs, case-insensitive deduplication excluding To. Validate on the server and reject stale recipient previews. Record CCs in the delivery and Gmail activity. No copied Elite organization address and no live lender emails during testing.
- [x] Use focused additive migrations only; do not replay historical migrations or seeds. Exercise real migration SQL in PGlite, run targeted regressions, full npm verify and Deno checks. Apply tested additions to linked hosted projects and deploy the changed Gmail function plus app.
- [x] Test production with clearly synthetic client/funder/note/document fixtures; confirm saved statuses and funder details, notes, scoped overview and full-size viewing. Verify preview recipients without sending to actual lenders. Remove fixtures, document evidence and keep existing PR draft pending historical migration reconciliation.

Review: preserve RLS/roles, validate every destination, no hidden CCs, no email from a status change or note, no edits to real client records for QA. The user's concrete client requirements authorize this implementation phase.
